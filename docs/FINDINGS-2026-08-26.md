## AEON-001 — Two audit tests fail under the default parallel test runner

**Severity:** minor (test-only; no production impact identified)
**Status:** reproduced, mechanism confirmed
**Files:** `crates/aeon-observability/src/audit.rs`
**Applies to:** BOTH working copies. `audit.rs` is byte-identical (260 lines) in
`D:\personal-github\aeon` (published, `ce783de`) and `D:\my-opensource\aeon` (249 commits,
divergent history, 3 days further on). Same two tests, same `static AUDIT_SINK` at line 105.
Verified by `cmp`, not assumed — the two trees differ in 31 entries elsewhere, so identity here
had to be checked.

### What happens

`cargo test --workspace` fails. Whole-workspace result: **1708 passed, 2 failed, 16 ignored**
across 59 suites. Both failures are in `aeon-observability`, and both are the same defect:

    ---- audit::tests::global_emitter_routes_to_installed_sink ----
    panicked at crates/aeon-observability/src/audit.rs:236:9
    assertion `left == right` failed
      left: 0
     right: 1

    ---- audit::tests::set_audit_sink_replaces_prior ----
    panicked at crates/aeon-observability/src/audit.rs:251:9
    assertion `left == right` failed
      left: 0
     right: 1

### The mechanism, confirmed rather than inferred

The audit sink is process-global:

```rust
static AUDIT_SINK: OnceLock<RwLock<Arc<dyn AuditSink>>> = OnceLock::new();

pub fn set_audit_sink(sink: Arc<dyn AuditSink>) { /* replaces the value */ }
```

Both tests install their own `Capture` sink via `set_audit_sink`, emit one event, then assert
their own capture holds exactly one event. Rust's test harness runs them **in parallel by
default**, so the two `set_audit_sink` calls race: whichever runs second replaces the sink, the
loser's `emit_audit` is routed to the winner's capture, and the loser asserts `1` against `0`.

The comment at `audit.rs:102` says the `RwLock` exists so tests can rebind the sink. The design
anticipated *rebinding*; it did not anticipate **concurrent** rebinding.

### Proof

Run serialised, the same tests pass:

    cargo test -p aeon-observability --lib -- --test-threads=1 audit::

    running 6 tests
    test audit::tests::global_default_is_null_sink ... ok
    test audit::tests::global_emitter_routes_to_installed_sink ... ok
    test audit::tests::null_sink_is_noop ... ok
    test audit::tests::set_audit_sink_replaces_prior ... ok
    test audit::tests::stderr_prefix_is_stable_public_constant ... ok
    test audit::tests::stderr_sink_serialises_via_json ... ok

    test result: ok. 6 passed; 0 failed

Six of six. The failure is entirely an artefact of shared global state under parallel execution.

### Why it is worth fixing rather than tolerating

It is **non-deterministic**. Which of the two tests fails depends on scheduling, so in CI it will
look like flake, get re-run until green, and train the team to disregard a red audit suite. A test
that fails randomly is worse than one that fails always: the second gets fixed.

It also makes `cargo test --workspace` **non-zero on a clean tree**, which means the exit status
cannot be used as a gate — every consumer of it has to special-case these two.

### Options, in the order I would consider them

1. **A test-local mutex.** A `static TEST_LOCK: Mutex<()>` in the test module, taken at the top of
   every test that touches the global sink. Smallest change, keeps the tests exercising the real
   global path, and states the constraint where a future test author will see it.
2. **`#[serial]`** (the `serial_test` crate). Same effect, more legible, adds a dev-dependency.
3. **Inject the sink instead of installing it globally.** Test `emit_audit`-equivalent logic
   against an explicit sink parameter and keep only one test for the global installation path.
   Largest change, and the only one that removes the shared state rather than serialising around
   it.

Option 1 or 2 is probably right: the global sink is a deliberate design decision — one process,
one audit destination — and the tests are correct to exercise it. The defect is the absence of
isolation between them, not the global itself.

### Not claimed

No production defect is asserted here. A running process installs its audit sink once at startup;
nothing in the tested paths rebinds it concurrently. The race is real but, on current evidence,
reachable only from the test harness.

> **Amended 2026-08-27.** The conclusion stands — the race is test-only — but the reason given
> above is wrong. A running process does **not** install its audit sink at startup, because
> nothing calls `set_audit_sink` outside the test module. That is a separate and larger defect,
> recorded below as AEON-002. The race is unreachable in production not because startup binds the
> sink once, but because production never binds it at all.

## AEON-002 — `set_audit_sink` has no production caller, so every audit event is discarded

**Severity:** major — security-relevant. A shipped binary emits audit events and writes none of
them anywhere.
**Status:** reproduced by exhaustive enumeration; mechanism confirmed
**Files:** `crates/aeon-observability/src/audit.rs`, and 13 call sites listed below
**Applies to:** BOTH working copies. The two `FINDINGS` trees are byte-identical here, as they
were for AEON-001.

### What happens

The audit sink is a process global with a null default:

```rust
static AUDIT_SINK: OnceLock<RwLock<Arc<dyn AuditSink>>> = OnceLock::new();

pub fn set_audit_sink(sink: Arc<dyn AuditSink>) { /* replaces the value */ }   // audit.rs:113
```

The crate's own test `global_default_is_null_sink` asserts the unset default is `NullAuditSink`,
and `null_sink_is_noop` asserts that sink discards what it is given. Both pass. So an audit event
emitted before anything calls `set_audit_sink` is silently dropped.

**Nothing calls `set_audit_sink` outside the test module.** Every occurrence in the workspace:

| location | what it is |
|---|---|
| `audit.rs:11`, `audit.rs:12` | doc comments |
| `audit.rs:113` | the definition |
| `audit.rs:231`, `:244`, `:245` | three calls, all inside `mod tests` |
| `audit.rs:241` | the name of a test function |
| `lib.rs:72` | the `pub use` re-export |

Eight occurrences, zero production callers. `aeon-cli` never calls it; nor does any other crate.

### Why that matters: the emitters were built and wired

This would be inert trivia if nothing emitted. It is not — **13 call sites across five crates**
emit into that global:

```
crates/aeon-connectors/src/http/webhook_source.rs:268          emit_auth_rejected
crates/aeon-connectors/src/quic/source.rs:150                  emit_auth_rejected
crates/aeon-connectors/src/webtransport/datagram_source.rs:149 emit_auth_rejected
crates/aeon-connectors/src/webtransport/source.rs:154, :219    emit_auth_rejected
crates/aeon-crypto/src/kek.rs:215, :235, :250, :262            emit_kek_audit  -> :303 emit_audit
crates/aeon-engine/src/erasure_store.rs:113                    emit_audit
crates/aeon-engine/src/pipeline_supervisor.rs:468              emit_audit
```

Five of those are **authentication rejections** — precisely the class of event an audit trail
exists to retain. Four are key-encryption-key lifecycle events. All are discarded.

The rejection paths still *work*: the request is refused, the connection is closed. What is lost
is the record that it happened. So this is not an authentication bypass; it is the total absence
of an audit trail behind working authentication, which is the harder failure to notice — the
control looks correct in every functional test.

### Scope, stated rather than overclaimed

A separate roadmap reconciliation run against `v0.2-canonical` found that the QUIC and
WebTransport connectors are not compiled into the shipped `aeon-cli` binary. If that holds, three
of the five auth-rejection sites are not reachable in the released artifact. The remaining eight —
webhook auth rejection, all four KEK events, the erasure store, the pipeline supervisor — are in
crates the binary does build, so the count of *reachable* discarded events is smaller than 13 and
larger than zero. The mechanism is unaffected either way.

I have not audited whether an operator-facing configuration key was intended to select a sink;
there is no such key in the manifest schema that I found, but absence-of-evidence is why this is
phrased as a question in the next section rather than as part of the finding.

### Proof

    grep -rn "set_audit_sink" crates/     # 8 hits, all listed above
    grep -rn "emit_audit\|emit_auth_rejected\|emit_kek" crates/ --include=*.rs \
      | grep -v aeon-observability        # 13 hits

Both were run against a clean checkout of each working copy and returned identical results.

### Options

1. **Install a real sink at startup.** `aeon-cli` bootstrap calls `set_audit_sink` with
   `StderrAuditSink` (already written and tested — `stderr_sink_serialises_via_json` passes) or a
   file sink, selected by config. Smallest change that makes the existing emitters useful.
2. **Make the default non-null.** Change the `OnceLock` default from `NullAuditSink` to
   `StderrAuditSink`, so the failure mode of forgetting to configure is noisy rather than silent.
   Inverts the current default toward safety.
3. **Fail closed at startup** when audit is required by config and no sink was installed.

Option 1 plus option 2 is the combination I would pick: an explicit choice when configured, and a
default that leaves a trace when nobody configured anything.

### A question for the maintainer, not a finding

Was the null default deliberate — audit-off-by-default, with sink installation intended as a
deployment-time responsibility that simply has not been written yet? The doc comment at
`audit.rs:11` says an operator "replaces it via `set_audit_sink` during bootstrap", which reads
like a bootstrap that was planned rather than one that exists. If it was deliberate, this finding
downgrades to "the bootstrap hook is unimplemented and undocumented as such". If it was not, the
severity above stands. **This is a question about intent and only you can answer it.**
